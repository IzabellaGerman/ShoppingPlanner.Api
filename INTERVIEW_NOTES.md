# Interview Notes — ShoppingPlanner.Api

Заметки по принятым решениям и концепциям. Каждый пункт — короткий ответ "почему так" в одно-два предложения, чтобы быстро освежить перед собеседованием.

Формат: **Концепция** → короткий ответ → (опционально) развёрнутая версия / типовые follow-up вопросы.

## Архитектура и паттерны

### Почему DTO отдельно от Model

Domain model (`Product`) — внутреннее представление сущности, связанное с БД и доменной логикой. DTO — то, что выставляем наружу через API.

**Зачем разделение:**
- Можно менять структуру таблицы в БД, не ломая публичный контракт API (и наоборот).
- Безопасность: никакие "лишние" поля модели случайно не утекают в JSON (например, `PasswordHash`, внутренние флаги).
- Разные DTO под разные операции: `CreateProductDto` без `Id` (его генерирует сервер), `UpdateProductDto` может отличаться от `CreateProductDto`, `ProductDto` для ответа клиенту.
- Валидация на DTO ≠ валидация доменной модели. На входе проверяем формат, в домене — бизнес-правила.

**Follow-up на собесе:**
- "Не дублирование ли это?" → Да, поначалу выглядит так, но они расходятся почти всегда при росте проекта. Лучше иметь чёткое разделение с самого начала, чем потом разделять задним числом.
- "Используешь AutoMapper?" → Пока маппинг руками — на маленьких DTO это явнее и не прячет логику. AutoMapper имеет смысл, когда DTO много и они большие.

### Почему `required` на полях модели

C# 11 добавил `required` — компилятор требует инициализировать поле при создании объекта. Защита от `NullReferenceException` ещё на этапе компиляции, плюс честно отражает намерение: "это поле обязательно".

**Альтернативы и почему `required` лучше:**
- `= string.Empty` — компилируется, но создаёт "тихо пустой" объект, баги ловятся в рантайме позже.
- `string?` (nullable) — врёт о намерениях: в домене продукт обязан иметь имя, nullable говорит обратное.
- `required string` — честно и безопасно.

Работает в паре с включёнными nullable reference types (по умолчанию в .NET 8 шаблонах).

**Follow-up:**
- "А если кто-то всё равно нарушит через reflection / десериализацию?" → `required` проверяется только компилятором при `new`. EF Core и `System.Text.Json` обходят это (что и нужно — иначе нельзя было бы загружать объекты из БД).

### Почему `DateTime.UtcNow`, а не `DateTime.Now`

Всегда храним время в UTC. Локальная зона — только для отображения на UI.

**Зачем:**
- Сервер может стоять в одной зоне, юзер — в другой. Если хранить `Now`, сравнение времён ломается.
- Переход на летнее время: один и тот же `DateTime.Now` может встретиться дважды или вообще не встретиться. UTC не имеет DST.
- Базы данных типа PostgreSQL имеют отдельные типы `timestamp with time zone` и `timestamp without time zone` — с UTC всё однозначно.

**Follow-up:**
- "А если нужно показать юзеру в его локальном времени?" → На клиенте конвертируем UTC → local через `TimeZoneInfo` или на фронте через `Date.toLocaleString()`.
- "`DateTime` vs `DateTimeOffset`?" → `DateTimeOffset` хранит смещение от UTC явно, надёжнее. Для новых проектов многие рекомендуют его. Но `DateTime` в UTC — тоже валидный выбор, главное — единый стандарт по всему проекту.

### Где устанавливать `CreatedAt` — в модели или в сервисе

В коде сейчас: `public DateTime CreatedAt { get; set; } = DateTime.UtcNow;` — дефолт прямо в модели.

**Плюс:** не забудешь установить, гарантия что всегда заполнено.

**Минус:** ответственность размазана. Когда EF Core грузит из БД, он создаст объект (сработает дефолт), потом перезапишет значением из БД — работает, но неявно.

**Production-варианты:**
- Явно в сервисе при создании: `new Product { ..., CreatedAt = DateTime.UtcNow }`.
- Через `SaveChangesInterceptor` в EF Core — автоматически проставляет `CreatedAt`/`UpdatedAt` для всех сущностей через единый механизм. Это правильный enterprise-подход.

### Зачем интерфейс для сервиса (`IProductService`)

Не сам сервис, а интерфейс к нему — это контракт. Контроллер зависит от `IProductService`, а не от конкретного класса.

**Что это даёт:**
- **Тесты:** в unit-тестах можно подсунуть мок (`Mock<IProductService>`) и проверять контроллер изолированно.
- **Замена реализации:** на неделе 3 заменим `ProductService` (in-memory) на новую реализацию с EF Core — контроллер не изменится ни строкой.
- **Принцип Dependency Inversion (SOLID):** высокоуровневые модули (контроллеры) не зависят от низкоуровневых (хранилище), оба зависят от абстракции (интерфейса).

**Follow-up:**
- "Не overkill ли интерфейс для одного класса?" → Для production-кода — нет, потому что тесты. Для одноразового скрипта — да, можно без интерфейса.

### `AddSingleton` vs `AddScoped` vs `AddTransient` в DI

Три времени жизни зависимостей в ASP.NET Core DI:

- **`Singleton`** — один экземпляр на всё приложение. Все запросы получают тот же объект.
- **`Scoped`** — один экземпляр на HTTP-запрос. Внутри запроса все потребители получают тот же объект, между запросами — разные.
- **`Transient`** — новый экземпляр каждый раз при разрешении зависимости.

**Когда что использовать:**
- `Singleton` — для stateless или для in-memory shared state (как наш `ProductService` сейчас).
- `Scoped` — для `DbContext` в EF Core. DbContext не thread-safe и должен жить ровно один запрос.
- `Transient` — для лёгких stateless объектов, где нет смысла кэшировать.

**Подвох:** нельзя инжектить `Scoped` или `Transient` в `Singleton`. Singleton переживёт scoped-объект, ссылка станет невалидной. ASP.NET Core ловит это при старте через "scope validation".

### Возвращать `IEnumerable<T>`, а не `List<T>` из методов сервиса

Контракт интерфейса должен быть максимально узким. `IEnumerable<T>` говорит "по этому можно итерироваться" — и всё.

**Зачем:**
- Реализация свободна вернуть массив, список, `yield return`-генератор, результат LINQ-запроса — потребителю всё равно.
- Принцип "программируй на интерфейсы, а не на реализации".
- Если бы метод возвращал `List<T>`, потребитель мог бы вызвать `.Add()` и неожиданно модифицировать внутреннее состояние сервиса.

**Follow-up:**
- "А `IReadOnlyList<T>` или `IReadOnlyCollection<T>`?" → Ещё лучше, если нужно явно гарантировать защиту от модификации и доступ к `.Count`. `IEnumerable` минималистичнее, но потребителю придётся материализовать через `.ToList()` если нужен индексный доступ.

### `FirstOrDefault` vs `First` и почему `is null` вместо `== null`

`First` → исключение, если не найдено. `FirstOrDefault` → `null` (или default для value-типов).

Для сценария "найти по id, может не существовать" — `FirstOrDefault`. Для "первый элемент непустого списка" — `First`.

**`is null` vs `== null`:**
- `==` может быть переопределён через перегрузку оператора в классе, и тогда `product == null` сделает что-то неожиданное.
- `is null` — паттерн-матчинг, его нельзя переопределить, работает всегда детерминированно.
- В современном C# идиоматично писать `is null` / `is not null`.

### Thread-safety в простом in-memory сервисе

Текущий `_nextId++` и `_products.Add(...)` **не thread-safe**. Два одновременных запроса могут получить одинаковый id или повредить состояние списка.

**Почему сейчас это окей:**
- Pet-проект, нет реальной нагрузки.
- На неделе 3 заменим in-memory на PostgreSQL через EF Core — auto-increment колонки в БД thread-safe by design.

**Как бы я решила, если бы это был production:**
- Для счётчика: `Interlocked.Increment(ref _nextId)`.
- Для списка: `lock` вокруг операций или `ConcurrentBag`/`ConcurrentDictionary`.
- Но правильный production-ответ всё равно — "перенести в БД".

**Follow-up на собесе:** *"Ты использовала Singleton с изменяемым состоянием — это безопасно?"* — Для текущего проекта да, потому что in-memory and low-stakes, но в production я бы либо вынесла состояние в thread-safe коллекцию, либо вообще убрала состояние из сервиса.
